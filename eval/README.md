# RAG 检索质量评测

用一组标注好的问题（golden set）量化「检索到底准不准」，让调参有依据，
而不是凭感觉改 `k` 和 `chunk_size`。

## 快速开始

```bash
# 1. 只校验 golden set，不调用任何 API —— 零成本，改完标注先跑这个
python -m eval.run_eval --validate-only

# 2. 正式评测（每条查询调用一次嵌入 API）
python -m eval.run_eval --k 1 3 5

# 3. 结果落盘
python -m eval.run_eval --k 3 --out eval/report.md --json-out eval/raw.json
```

## 指标

| 指标 | 含义 | 什么时候看它 |
|---|---|---|
| **Hit@K** | Top-K 里是否至少命中一个期望文档 | 最直观，「用户能不能找到」 |
| **Recall@K** | Top-K 覆盖了多少比例的期望文档 | 允许多个正确答案时用它 |
| **Precision@K** | Top-K 中有多少比例是期望文档 | 看检索有没有塞垃圾 |
| **MRR** | 第一个命中排在第几位的倒数均值 | 看「正确结果排得够不够前」 |
| **MAP** | 平均精度，同时惩罚排得靠后和漏召 | 综合指标 |

## 度量口径

几个刻意的设计选择，问「怎么测的」时可以照这段答：

**① 按主题名匹配，不按文件名。**
语料里同一主题存在多种格式（`blockchain_basics` 同时有 `.md` / `.docx` / `.pdf`，
内容相同）。要求命中特定格式没有意义，所以匹配单位是**去掉扩展名的主题名**。

**② K 指的是 chunk 条数，与线上行为一致。**
应用本身就是取 top-k 个 chunk。计算文档级指标前会按主题去重，
避免同一篇文档的多个 chunk 挤占多个排名位。

**③ 走纯检索路径，不经过查询改写。**
评测直接调 `rag.retriever.retriever()`。golden set 里的问题都是自包含的，
不依赖多轮上下文，所以改写环节不该介入——否则测的就不是检索本身了。

**④ 无论评估几个 K，检索只跑一次。**
MMR 是贪心选择，前 k 个结果具有前缀稳定性，所以 `--k 1 3 5` 和 `--k 5`
的 API 调用次数相同。

## golden set

`golden_set.json`，44 条查询，覆盖语料中的全部 44 个主题。

```json
{
  "query": "区块链上的数据为什么改不了？",
  "expected": ["blockchain_basics"],
  "note": "考察哈希链与共识机制，措辞与原文不同"
}
```

**提问原则：不照抄文档标题或正文原句。** 字面重叠会让指标虚高——
关键词完全重合的话，连最笨的检索器都能命中，测不出真实能力。
所以刻意用口语化、描述性的说法（比如用「新用户没有任何历史行为」
来问冷启动，全文不含这个词）。

**新增查询后必须跑 `--validate-only`**，它会检查期望主题是否真的存在于语料中
（写标注时很容易把生成脚本里的主题清单和实际语料记混）。

## 成本

| 操作 | 调用量 | 说明 |
|---|---|---|
| `--validate-only` | 0 | 只读文件 |
| 正式评测 | 每条查询 1 次嵌入 | 查询很短，费用极低 |
| 单元测试 | 0 | `tests/test_eval_metrics.py` 全用假数据 |

DeepSeek 有空闲时段半价（见项目根目录 `CLAUDE.md`），批量跑建议避开
工作日 9:00–12:00 与 14:00–18:00。

## 目前的局限

- **只评检索，不评回答质量。** 没有测「答案是否忠于原文」「有没有幻觉」。
  要做需要 LLM 判分，成本高一个量级，暂未实现。
- **没有负样本。** golden set 里每条查询在语料中都有答案，
  测不出「库里没答案时会不会硬编一个」。
- **chunk_size 对比需要重建索引**，会重新嵌入整个语料，成本远高于查询侧评测，
  建议单独安排时段跑。
