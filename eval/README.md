# RAG 检索质量评测

用一组标注好的问题（golden set）量化「检索到底准不准」，让调参有依据，
而不是凭感觉改 `k` 和 `chunk_size`。

## 快速开始

```bash
# 1. 只校验 golden set，不调用任何 API —— 零成本，改完标注先跑这个
python -m eval.run_eval --validate-only

# 2. 正式评测（每条查询调用一次嵌入 API）
python -m eval.run_eval --k 1 3 5

# 3. 结果落盘
python -m eval.run_eval --k 3 --out eval/report.md --json-out eval/raw.json
```

## 指标

| 指标 | 含义 | 什么时候看它 |
|---|---|---|
| **Hit@K** | Top-K 里是否至少命中一个期望文档 | 最直观，「用户能不能找到」 |
| **Recall@K** | Top-K 覆盖了多少比例的期望文档 | 允许多个正确答案时用它 |
| **Precision@K** | Top-K 中有多少比例是期望文档 | 看检索有没有塞垃圾 |
| **MRR** | 第一个命中排在第几位的倒数均值 | 看「正确结果排得够不够前」 |
| **MAP** | 平均精度，同时惩罚排得靠后和漏召 | 综合指标 |

2026-09-15 评测，语料 62 篇 / 398 个 chunk，44 条查询，嵌入模型 `qwen3.7-text-embedding`：

| K | Recall@K | Hit@K | Precision@K | 未命中 |
|---|---|---|---|---|
| 1 | 0.920 | **0.932** | 0.932 | 3 |
| 3 | 0.966 | **0.977** | 0.326 | 1 |
| 5 | 0.966 | 0.977 | 0.195 | 1 |

MRR **0.955**　MAP **0.943**

即：44 条查询里有 41 条的 top-1 就是正确文档。

> 换嵌入模型前（`text-embedding-v4`）这里写的是 Hit@3 0.955 / MRR 0.943 / MAP 0.932。
> 换用 `qwen3.7-text-embedding` 后 Hit@1 持平，K≥3 少一条未命中，MRR/MAP 一致更好——
> 上面是新模型的数字，且已用 `raw.json` 逐条复算核对过。选型依据见 `notes/评测与术语速查.md` 第九节。

### 未命中案例的归因

光给失败数字没有价值，所以逐个看了原因。

**①「容器和虚拟机相比省在哪里？」→ 召回 `cloud_computing`，应为 `docker_container`**

`docker_container.txt` 第一段就写着「相较于传统虚拟机需要模拟完整操作系统，
Docker 容器直接共享宿主内核」，是直接答案。但两份文档都出现「虚拟机」，
**检索被字面重叠带偏了**。

**②「机器是怎么把一段文字变成一串数字的？」→ `embedding_models` 连前 5 都没进**

`embedding_models.pdf` 里写的是「把一段文字映射成固定维度的实数向量」——
语义完全对应，但「数字」与「向量」用词完全不同。这是语义检索的典型失败模式：
**口语化改写与文档术语之间的词汇鸿沟**。

**③「普通人怎么防范钓鱼网站和电信诈骗？」→ 召回 `legal_common_sense`（K=3 时已修正）**

期望的 `network_security` 在 top-3 内被召回，属于**排序问题而非召回失败**。

> 案例 ② 没有被文过饰非地改掉。口语化提问是真实用户会做的事，检索不到就是检索不到——
> 把它从评测集里删掉只会让指标好看、让评测本身失去意义。

## 度量口径

几个刻意的设计选择，问「怎么测的」时可以照这段答：

**① 按主题名匹配，不按文件名。**
语料里同一主题存在多种格式（`blockchain_basics` 同时有 `.md` / `.docx` / `.pdf`，
内容相同）。要求命中特定格式没有意义，所以匹配单位是**去掉扩展名的主题名**。

**② K 指的是 chunk 条数，与线上行为一致。**
应用本身就是取 top-k 个 chunk。计算文档级指标前会按主题去重，
避免同一篇文档的多个 chunk 挤占多个排名位。

**③ 走纯检索路径，不经过查询改写。**
评测直接调 `rag.retriever.retriever()`。golden set 里的问题都是自包含的，
不依赖多轮上下文，所以改写环节不该介入——否则测的就不是检索本身了。

**④ 无论评估几个 K，检索只跑一次。**
MMR 是贪心选择，前 k 个结果具有前缀稳定性，所以 `--k 1 3 5` 和 `--k 5`
的 API 调用次数相同。

## golden set

`golden_set.json`，44 条查询，覆盖语料中的全部 44 个主题。

```json
{
  "query": "区块链上的数据为什么改不了？",
  "expected": ["blockchain_basics"],
  "note": "考察哈希链与共识机制，措辞与原文不同"
}
```

**提问原则：不照抄文档标题或正文原句。** 字面重叠会让指标虚高——
关键词完全重合的话，连最笨的检索器都能命中，测不出真实能力。
所以刻意用口语化、描述性的说法（比如用「新用户没有任何历史行为」
来问冷启动，全文不含这个词）。

**新增查询后必须跑 `--validate-only`**，它会检查期望主题是否真的存在于语料中
（写标注时很容易把生成脚本里的主题清单和实际语料记混）。

## 成本

| `--validate-only` | 0 | 只读文件 |

## 目前的局限

- **本文件只覆盖检索评测。** 回答质量（答案是否忠于原文、有没有幻觉）在
  [`gen_eval.py`](gen_eval.py) 里单独评 —— 三层设计：资料忠实度 → 逐条事实核查
  → Tavily 联网核实，44 条 × 3 轮。**那个评测自己也有已知局限**
  （裁判会判错、区分不了事实与观点），见它的文件头说明。
- **没有负样本。** golden set 里每条查询在语料中都有答案，
  测不出「库里没答案时会不会硬编一个」。
- **chunk_size 对比要重建索引**，会重新嵌入整个语料，成本远高于查询侧评测。
  已做过一轮，工具在 [`experiment.py`](experiment.py)，建议单独安排时段跑。
